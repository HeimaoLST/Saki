# Desktop workbench：联系人式 GUI 原型

更新日期：2026-10-22。状态：**设计提案，可交互原型；未实现为原生 GUI**。设计负责人 `agent:pm#mira`，任务 [#124](https://github.com/HeimaoLST/Saki/issues/124)。

打开 [desktop-workbench.html](previews/desktop-workbench.html) 查看 Moon / Dawn、日常气泡对话、表格与图表、安静工作、边工作边说话、无消息完成、工作受阻、启动异常和空对话，以及右侧工作区、文件预览和历史／设置面板。默认展示三栏安静工作场景。页面上方为设计审阅控件，不属于产品。原型没有网络调用，不启动 Agent，不修改真实配置；所有对话和状态均为模拟。

## 设计目的与依据

保留现有「联系人 → 对话 → 输入」结构，让第一次打开容易理解，长时间使用仍便于阅读和检查执行过程。参考产品的实际观察与限制见 [Grok Bot / Qoder 调研](../research/systems/desktop-interaction.md)。本原型采用现有 mascot 与 Moon / Dawn 语义角色，不决定 GUI 新名字。

实现事实基线为 [`dev@47d01ee`](https://github.com/HeimaoLST/Saki/tree/47d01ee83972f8459167503001656a12f9f87c6c/desktop)：220px 联系人侧栏、居中阅读列、History / Settings、工具 Details、贴底 composer、联系人的草稿及 Runtime 任务状态。实际行为以 [desktop.md](desktop.md) 为准。需求参考 [#111 的固定版本](https://github.com/HeimaoLST/Saki/blob/28eb6952cb013dbfb340789ac256e8953a6aff55/docs/requirements/desktop.md)，不假定 PR #119 已集成。

## 美学规则

视觉方向是温暖、安静、细节清楚。根据用户 2026-10-22 的反馈，本版以连续的双方消息气泡组织对话：用户消息靠右、助手消息靠左；保留每次来回与消息归属，长内容也在消息内部排版。此前将助手回复铺成文档正文的方案已被本版替代。

| 项目 | 原型提案 |
| --- | --- |
| 布局 | 三栏：左侧联系人 192px、中间弹性对话、右侧工作区 360px；紧凑桌面下两侧改为 160px / 320px。工作区展开时阅读列左右留白各 20px，收起时恢复 86% 阅读宽度，最大 760px |
| 字体 | 系统 sans-serif；消息正文 14px / 1.7；次级文字 12–13px；名称 15px semibold；气泡内小标题 14px；代码系统 monospace |
| 间距 | 消息之间 18px；气泡内边距 12px / 16px；段落间 10px；头像与消息间 9px |
| 头像 | 沿用共享 mascot；侧栏 32px，标题与助手消息 28px；不通过不同头像暗示尚未实现的人格能力 |
| 容器 | 双方消息圆角 18px、靠近发送者一角 4px；用户气泡最多占阅读列 78%，助手富文本可用头像之外的剩余宽度；composer 18px |
| 强调 | rose 用于发送按钮；用户气泡使用 rose 18% 与 Surface 混合，正文仍用 Text；助手气泡使用 Base 与轻边框；状态用 Success / Warning / Danger |
| 控件 | 桌面鼠标使用的图标入口至少 32px，主要动作 36px；有可读名称和可见焦点，不只靠悬停提示 |

色彩权威定义继续使用 [desktop.md 的主题系统](desktop.md#主题系统92-设计)，原型只映射已有角色。Moon base `#232136`，Dawn base `#faf4ed`；文字、muted、状态色采用该文档中已区分官方与派生的数值。原型不创建第二套主题加载或持久化设计。Dawn 的 rose 按钮使用深色文字，不能直接换成白字。

## 界面与状态

| 场景 | 呈现与交互 | 契约／后续实现 |
| --- | --- | --- |
| 日常对话 | 连续来回、左右气泡、助手身份、消息时间与复制；短消息按内容收缩，发送追加记录 | 每条真实消息对应一个气泡，不按句子伪造多条消息；消息时间只显示已知事实，不虚构已读 |
| 表格与图表 | 单个助手气泡内含段落、表格和图表；表格适应气泡宽度、单元格自动换行，表格和图表均可展开查看 | Markdown / copy 对接 #113；图表是新增设计提案，尚未验证原生组件，不自动扩大 #113 的实施范围 |
| 工作中 | 联系人与页头显示执行状态；右侧工作区承载当前工作、资料、产物与执行记录；停止属于当前工作 | 只能由 `task_started` 进入工作中；消息出现不代表工作结束；本原型选择器模拟事件 |
| 停止 | 点击后先显示「正在停止」，最终显示「已停止」并保留已有内容与新草稿 | 原型延时只为演示；原生必须等待 `task_finished`，不能按计时器判成功 |
| 启动异常 | 持续展示失败阶段、可执行下一步和诊断详情；输入保留但禁止发送 | 对接 #112；不新增重连服务、凭据编辑器或假 Reload |
| 空对话 | 简短欢迎与输入区；添加联系人即选中并聚焦，不先要求配置 | 沿用现有创建逻辑 |
| 历史 | 右侧过滤已有记录，选中后返回对应对话位置；关闭恢复入口焦点 | 原型只搜索虚构 fixture；不承诺新的 Runtime 检索接口 |
| 设置 | 联系人名与已绑定 profile 分开；只读字段说明何时生效；外观属于应用级 | 绑定后 profile 约束沿用当前实现；外观 #96 |

原型允许切换联系人并保留各自草稿；一个联系人工作中时，另一个联系人可查看／编辑但不可并发发送。尚未接入 #118 前不展示多联系人同时执行。模型切换、连接编辑、附件、通知、日程和第三方扩展不在本原型范围。

## 气泡中的富文本

气泡表示消息归属，内容区域负责渲染；两者独立。保留段落、列表、小标题、链接与行内代码的正常阅读顺序。示例中的短回复由作者按对话语气编写，真实应用不能为营造聊天节奏擅自截断或拆分模型回复。

- 表格：默认适应气泡宽度，单元格自动换行、保留表头与行列关系，**不把横向滚动作为默认阅读方式**。原型中的四列表格提供“展开查看表格”，在更宽浮层中阅读；Esc 关闭并返回入口。用户明确认为横向移动会打断阅读，因此替代早期原型的横向滚动方案。对于列数更多、窄屏下已无法辨认的内容，纵向字段卡片作为后续候选；本版未实现自动转换，也不隐藏列。
- 图表：气泡内先嵌入可读的图形，注明数据含义与单位；提供放大入口。放大后 Esc 关闭，焦点返回入口。原型为本地 SVG 条形图，包含文字等价说明，**没有 Markdown 解析器、Mermaid 引擎或通用图表渲染器**。
- 展开：工具输出归入独立工作视图，默认折叠；可独立展开的补充安排按消息作者组织折叠。主回复不统一截断为“查看更多”，也不把整个消息改为嵌套的纵向滚动框。
- 消息追加：用户发送只追加用户消息；只有模拟 Agent 发消息才新增助手气泡。模拟工作完成／停止只改变工作记录，已有消息保留。审阅栏中的模拟动作仅用于演示，不属于产品操作。

原生开发需核对 MyGo 对表格布局、选择／复制、自适应表格、图形与展开视图的支持。图表数据格式与渲染器选择需另定范围；这属于 GUI 内容展示，不要求 Agent Runtime 负责绘制或引入联系人概念。

## Agent 的工作与消息（产品方向已确认，呈现方案待验证）

用户明确要求将 Agent 视为可以独立做事的联系人：它可以工作而不发消息，消息是沟通行为，不能作为工作存在或完成的前提。**一次工作可以产生零条、一条或多条对用户的消息；工具过程归属于工作，不归属于某条回复。** 这替代此前“工具状态附在本次回复下”的提案。第 04 版 HTML 以独立工作记录和消息列表模拟这一关系；工具过程、资料与产物集中在右侧工作区，界面方案供用户审阅，未实现为原生 GUI。

建议的界面职责：

| 位置 | 展示什么 | 不依赖什么 |
| --- | --- | --- |
| 联系人列表与页头 | Agent 当前工作状态，例如“正在整理资料”；工作入口持续可发现 | 不以是否生成消息判断它是否工作，不把“工作中”写成“正在输入” |
| 对话区 | 用户和 Agent 真正发出的消息，按时间排列为气泡 | 工具开始、结束、运行完成均不自动生成聊天气泡或占位回复 |
| 右侧 Agent 工作区 | 当前／最近工作的目的、状态、资料、产物、执行记录与停止操作；文件在同一侧栏预览，工具详情按需展开 | 无聊天输出时也能查看、完成和恢复查看工作记录；不要求找到一条对应回复 |

沟通与状态分开处理：

- 安静工作：收到委托后可以只更新工作状态，持续执行工具；若没有对用户的消息，对话保持原样。完成时更新工作记录与产物，不强制补“已完成”消息。
- 需要交流：询问用户、提出需用户决定的问题、传达值得告知的结果，作为真实消息出现。GUI 不依据工具输出猜测并伪造 Agent 发言；何种输出属于发给用户的消息，应在 Agent／宿主的沟通契约中明确。
- 未读与注意事项：聊天未读来自真实新消息；后台工具调用、普通完成不累加聊天未读。失败／阻塞显示独立的“需要处理”状态与可执行下一步，是否额外发消息依产品沟通策略决定，重要问题不能因无消息而消失。
- 同时说话与工作：一条进度说明或询问不代表工作结束；收到文本不能替代运行终态。消息可关联具体工作以便追查，但工作在没有消息时仍完整存在。

**实现事实（原型基线 `dev@47d01ee`）**：[`AgentEvent`](../../src/agent/mod.rs) 已区分 `ResponseText`、`ToolStarted`、`ToolFinished`；[`process_messages`](../../src/agent/mod.rs) 分别处理 `OutputItem::Message` 和 `ToolCall`，工具分支不要求先出现文本。机器接口的 `message_id` 关联输入，文本 `item_id` 与工具 `call_id` 分别关联到 task；见 [Runtime API](runtime-api.md)。[`desktop/runtime_model.go`](../../desktop/runtime_model.go) 中 `liveText` 与 `liveTool` 分别创建记录，但都放入 `ct.Messages`；`task_finished` 对未选联系人增加 `Unread`。这些是展示／通知解耦需要核对的现状，不等于已经实现安静工作产品语义。

当前机器入口仍通过 `task.send` 的输入启动任务；自主触发、定时工作、应用关闭后继续执行、主动通知等并未由本设计宣称实现。当前先明确工作与沟通的关系，未来具体触发和生命周期按需求分别设计，不据此立即引入调度服务或扩大 Runtime 范围。原型场景已覆盖：只执行工具但无新消息、工作中主动发一条消息后继续执行、无消息完成、无消息失败仍可发现与处理。只有一条当前／最近工作记录用于设计演示，不代表完整工作历史产品已实现。

### 本项产品需求的验收标准

1. **无消息也可观察**：Agent 持续调用工具但没有发消息时，联系人与页头显示工作状态；打开工作视图可看实际动作，不出现占位聊天气泡。
2. **交流不结束工作**：工作中 Agent 发来一条消息，聊天新增气泡，工作仍保持运行；只有运行终态更新执行结果。
3. **无消息也可完成**：工作完成但没有发消息时，消息数量保持不变；工作记录标为完成，产物仍可查看。
4. **操作归属工作**：查看、停止作用于选中的工作；停止请求与停止终态分开，已有消息、草稿和执行记录保留。
5. **问题独立可见**：工作失败或需要用户处理时，即使没有聊天消息也显示“需要处理”、原因和下一步；恢复后的错误不持续误报为整项工作失败。
6. **消息与通知不混用**：工具调用和普通完成不制造聊天未读；真实 Agent 消息才进入消息未读逻辑。原型未模拟未读计数，原生交付必须验证。

第 04 版的“模拟 Agent 发消息”和“模拟工作完成”是独立控件，可在同一项工作上依次操作。原型沿用当前单任务输入边界：工作中可编辑草稿，发送暂不可用，停止位于右侧当前工作卡片。工作过程中用户新消息如何递交给正在执行的 Agent，需要进一步明确 Runtime／宿主输入契约；此限制不作为最终产品需求定案，也不通过假队列宣称已经解决。

## 三栏布局与右侧工作区（第 04 版提案）

用户提供的 Qoder 截图显示了左侧导航、中间交流、右侧可折叠工作空间。本设计采纳这种空间分工：**联系人 → 对话 → Agent 工作区**。右侧在桌面宽度与对话并排，属于可折叠侧栏（side panel）；窄窗口覆盖对话时才采用模态抽屉。截图仅能支持布局观察，不据此推断 Qoder 的交互、动画或内部实现。

右侧集中三类内容：

- **当前工作**：工作目的、真实执行状态、最新动作、停止；不通过工具数量推算总体进度，也不展示推测的思考过程。
- **资料与产物**：已读取资料可以查看，读取中／未找到的资料如实显示状态；只有实际生成后才出现产物。预览在右侧打开，可返回工作概览或展开阅读；中间仍保留原来的对话。
- **执行记录**：简短动作摘要，按需展开工具名、目标与输出。它是工作区的一部分，不占据整段聊天，也不是工作区唯一内容。

交互约束：

1. 工作区可随时收起／展开；收起不停止执行，不删除消息、草稿、资料或产物，页头与联系人仍显示状态。
2. 切换联系人时，已展开的侧栏跟随当前联系人；无工作记录时展示空态，不能混入其他联系人的资料。返回原联系人时工作记录仍可查看。
3. 文件预览与聊天独立滚动；返回概览恢复文件入口焦点。展开阅读时使用模态视图，Esc 先关闭最上层内容，不连带收起工作区。
4. 右侧停留在文件预览时，Agent 发消息不会关闭文件；工作完成不会自动追加回复，也不强制跳走当前预览。
5. 原型的场景选择器会重置示例，并在桌面宽度打开工作区以便审阅；这属于设计控件，不代表产品每次工作开始都强制打开侧栏。

本版仅展示与当前／最近一项工作关联的资料与产物，没有新增完整文件管理器、终端、浏览器、并行任务系统或编辑器。它为后续应用能力提供空间，不据此扩大本次生产实施范围。

## 动效与焦点

以下是**设计提案**，不是参考产品的测量结论：

- hover / pressed 的颜色反馈约 120ms；面板出现用 160ms opacity + 小幅位移。不对正文宽度进行长时间动画，避免字行反复换行。
- 打开面板保持空间来源；关闭后焦点回到原入口。按 Escape 关闭当前面板。模态面板使用浏览器原生 dialog 管理焦点；较宽布局的非模态侧栏不锁住主对话焦点。
- 运行状态用小型状态标记与文字，不让整段正文跳动；第 04 版使用静态圆点。减少动态效果开启时取消面板位移动画，保留状态文字。
- 草稿 Enter 发送、Shift+Enter 换行；输入法 composition 中 Enter 不发送。原型代码检查仅说明模拟行为，真实系统 IME 验收仍由 #114 完成。
- 状态改变通过短 live region 公告；不把整段流式正文反复播报。错误同时给出原因与下一步。

布局提案：应用实际宽度 ≥960px 时，工作区占独立列；≥1120px 使用 192px 联系人栏和 360px 工作区，其余桌面宽度使用 160px / 320px。低于 960px 时工作区改为模态覆盖，避免继续压缩消息正文；关闭后返回工作区入口。历史／设置仍是临时模态面板，关闭后回到原来的三栏状态，不替换 Agent 工作区。开发需验证 MyGo 的焦点、遮罩与 Esc 支持，浏览器行为不等于原生实现证据。

## 开发交接与验收

PM 负责原型、视觉规则、交互状态、文案与设计复核；GUI 主责负责 Go / MyGo 实现及真实窗口验证。原型是设计参考，不应整体移植成另一个应用框架；Runtime 仍只提供执行事实和公共能力。

开发验收至少覆盖：两色的正常／工作／错误状态；960×640、1040×720 与宽窗口；工作区收起后继续执行、重新打开后记录保留；切换联系人不串资料；文件预览与气泡对话可同时查看；模态关闭不连带关闭下层；面板不遮挡其关闭操作；长中文、长路径与代码不撑破布局；表格自动换行且无需横向移动；表格／图表展开与 Esc 焦点返回；键盘可操作且焦点可见；发送保留前序消息，选中联系人与草稿隔离；停止请求和最终停止分开；真实 IME 与发送语义不回归。图表项是设计验证要求，待单独确定生产实施范围。截图需注明原生或浏览器、被测提交及窗口尺寸。

本轮浏览器检查和截图在 PR 的证据部分记录；它只验设计原型，不替代 #112 / #113 / #114 / #96 的产品交付或真实用户试用。
