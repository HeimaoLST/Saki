## 产品定义

**Nagi 是一个开源的、以长期 Agent 联系人为核心的桌面工作台。用户通过持续对话交代事项，联系人理解意图、组织工作并自主推进；用户可以随时补充要求、了解进展或深入参与具体执行。**

产品以 Grok Bot 式的完整使用体验为参照。开源和好用本身构成当前产品方向，不以发明竞品没有的交互为前提，也不承诺复制竞品全部功能、服务或性能。源代码开放如何对应许可、安装、分发和部署方式，需分别落实，不能从“开源”直接推导为任意模型可用或无需配置。

第一批用户是维护者及朋友。面向需要持续委派工作、减少逐步指导负担的人；编程、资料整理和研究都可以成为使用场景，当前未冻结单一垂直领域。代码阅读、文档整理和登录接口只是讨论／验收示例，不表示用户已经选定全部首批试用任务。

主要价值是：用户能找到持续负责的联系人；交代的事情可被跟进；执行中能继续交流；成果和未解决问题可检查。安装、配置、首次委派、补充要求、获取结果与后续继续应形成可用流程。

## 三个产品的关系

| 产品 | 职责与默认使用方式 |
| --- | --- |
| Saki | 通用 Agent Runtime，提供模型／工具执行、上下文、会话、事件与调度等共同基础，让应用开发者聚焦自己的产品；跨应用协作是发展目标 |
| Nagi（GUI 暂定名） | 联系人式桌面工作台，默认侧重用户委派、联系人自主推进和必要时反馈；它是有自身产品规则的应用 |
| TUI（名称待定） | 终端中的执行与协作入口，默认侧重用户直接观察、指导和参与工作；继续复用 Saki 的运行能力 |

自主推进与人工介入可以发生在同一项工作中；这不是 GUI 与 TUI 的能力禁区划分。目标体验是从 GUI 进入某项具体执行，在 TUI 继续参与，再回到 GUI 查看同一事项的进展，无需用户复制上下文或重新派发。共享一套 Runtime 实现尚不足以证明这个跨端流程已经实现；交付时需验证同一工作归属、状态与操作的一致性。

## 核心概念与关系

| 概念 | 产品含义与边界 |
| --- | --- |
| 联系人 X | 持续存在的协作对象，有自己的职责、工作要求和关系上下文。可以承接一次具体需求，也可以长期负责一个领域；不等于一个永不更换的 session |
| 事项（Task / Issue） | 用户希望完成的一件事，包含目标、相关要求、当前进展和结果。Task 与 Issue 在产品层为同一语义，不据此建立父子层级；一件事项可以跨多次交流与执行 |
| 对话会话 | 用户与 X 持续交流的上下文，用于理解意图、补充信息、协调事项和反馈结果；普通讨论不必自动变成事项 |
| 执行会话 | 承载某项具体工作的独立上下文与历史，可持续多次执行。X 为其组织相关要求和资料，并在需要时传递后续信息；不是完整复制所有聊天记录 |
| 工作分身 | 对“同一联系人 X 在独立执行会话中工作”的解释方式，不要求用户再创建一个联系人，也不意味着必须新增一种底层 Agent 类型 |
| 一次执行 | 运行时的一次受理、模型／工具调用到终态的过程。既有 Runtime `task_id` 标识这种执行，不能直接当作产品事项 ID；本文不修改已有协议名 |

X 对用户承担事项的持续跟进，也可以通过自己的执行会话直接完成工作。监督与执行是同一联系人在不同上下文中的职责，不强制建立“经理联系人 → 执行联系人 → 子任务”的固定层级。

一项具体的登录接口需求可以由 X 在一个执行会话中完成，不必继续拆成用户需要管理的子事项。只有独立交付、并行工作或明确专业分工有价值时才拆分或协作；拆事项、开会话和委派另一 Agent 是不同操作，不能互相自动推导。

用户把事项交给 X 时，X 是可追问进展和结果的负责联系人。协作不应让用户失去负责人，也不应在不同视图中生成同一事项的互不关联副本。跨联系人转交、共同负责与全局／项目归属的具体规则尚待设计；本文不把事项的存储位置强行定在某个联系人之下。

## 主要使用流程与行为需求

本节将已确认方向整理为可验收的目标行为，不表示下列能力都属于已交付版本。P 编号描述产品目标；后文 G 编号保留现有阶段工程验收。

| ID | 流程与要求 | 验收场景 |
| --- | --- | --- |
| P1 | 创建或选择联系人即可交流；职责与工作要求可逐步明确 | 宿主基础配置有效时，新联系人可直接接受首条请求；用户不必先填写完整角色设定 |
| P2 | 联系人承接具体事项，能组织要求并直接执行；领域职责可以对应多件事项 | 将“实现登录接口”交给 X，能找到该事项的要求与进展；不为了满足内部层级而强制再创建执行联系人或子事项 |
| P3 | 执行工作与对话分别保持可用；X 为每项工作组织独立上下文 | X 推进事项 A 时，用户仍能讨论或交代 B；B 的要求不自动混入 A，也不因对话切换丢掉 A 的进展。并发数量由明确运行边界约束 |
| P4 | 对话中的补充能够关联并影响正确事项，用户能判断是否已经应用 | A 执行中，用户要求登录方式改为短信验证码；X 保留这次变更并递交给相关执行会话，区分已收到与执行已采用。尚未采用、需要重启工作或存在歧义时明确反馈；不把整段聊天广播给所有事项 |
| P5 | 工作与消息独立：一次工作可以发零条、一条或多条消息 | 仅调用工具或无消息完成时，工作区仍可查看状态与结果；工作中发出消息不会结束执行。未读来自真实消息，失败或待处理问题在没有消息时仍可发现 |
| P6 | 联系人持续跟进多件事项；执行结束与事项完成分开判断 | A 生成草稿但仍缺用户要求的内容时，事项保留未满足部分；B 等待资料时不会消失。查看事项可找到要求、补充、结果和完成依据，取消与完成有区别；不默认每项都新增人工审批 |
| P7 | 用户可以检查和干预具体工作，随后继续由 X 跟进 | 查看某项执行、补充要求或停止时，对象明确，不误操作其他事项。停止执行不自动删除事项、历史或已经产生的结果；暂停／继续的具体机制另定 |
| P8 | GUI 与 TUI 可围绕同一工作协作，避免重复派发 | 从 GUI 的事项进入对应执行，在 TUI 继续指导后，GUI 能反映同一工作的变化；交还后 X 能继续跟进。该流程的入口、控制协调和首发范围待定，不能只用两端都能启动证明通过 |

代表性完整场景：用户让 X 实现登录接口；X 在独立执行会话中推进；用户继续和 X 讨论，并补充验证码要求；X 更新相应事项并将变更交给执行；需要时用户深入查看或指导；最终在该事项下找到满足要求的结果和仍未解决的问题。该场景用于检验流程，不将 Nagi 的用途限定为编程。

## 首个可用 MVP 的交付边界

更新于 2026-10-25。**已确认产品要求**：用户明确要求基本功能完整、可正常独立使用的第一版产品，并要求提供文档和具体 issue 供 agent 追踪。本节取代 2026-10-24 的有限试用边界；其中“文件配置即可”“补充只保存/手动下次递交即可”“基本配置与资料输入可推后”不再作为最终 MVP 完成标准。已有实现切片及其证据继续有效，但只证明各自范围，不追溯扩称完整 MVP 已完成。

**MVP 定义**：在声明支持的环境中，用户独立完成安装和界面配置，建立长期联系人，通过对话交办真实事项；联系人自主推进并持续跟进，执行中可继续交流、补充要求和资料；用户能查看实际成果、干预或继续工作，并在异常和重启后恢复同一事项。正常流程不依赖开发者修配置文件、数据库或手工拼接会话。

**实施基线，待实现与验收**：首发聚焦 macOS arm64、Go/MyGo 桌面、本地应用运行期间的工作，以及明确验证过的模型/协议组合。基础资料先支持命名文字和 UTF-8 文本文件；其他格式如不支持，应在操作前明确反馈。新模型/provider 不能仅因兼容 API 名称而列为已支持。TUI 维护既有能力，Runtime 按 Nagi 实际缺口演进。

### 事项、联系人与自主跟进的最小规则

- 联系人是长期协作对象。用户可以在对话明确交办，必要时一次确认事项/目标；不能要求再抄到独立表单。普通聊天不自动建事项，具体的小需求不强制拆分或新增联系人。
- 事项至少能区分未开始、进行中、等待用户补充、需处理、已完成、已取消；归档是可恢复的组织操作。内部枚举可不同，但这些用户可观察状态与操作必须存在。停止一次执行不删除事项，继续是在同一事项内发起后续执行，不冒称恢复了已经结束的工具进程。
- 要求、补充、执行输入快照和实际结果保持关联。完成依据可来自可核对的输出/文件/检查记录或用户明确判断；无依据的要求保持未核实。自动完成必须有可检查依据，不强制每项新增人工审批。
- 对话 X 按需取得自己负责事项的目标、进展、待解决要求和结果；对话/详情/模型操作共用一套事项事实和动作。不能只把聊天与执行拆成两个 session 就声称监督能力已实现。
- 执行以相关目标、有效要求、选定资料和必要历史组装上下文，不复制全部聊天/工具日志、不将 B 的讨论广播给 A。最小实现允许每事项一个活动工作会话；并发槽需留出对话可用空间，实际拒绝/等待可见，不靠无限隐藏队列。
- 联系人自动推进已授权工作；缺信息时提出关联问题，得到答复后继续。重复失败、没有进展或需要新增授权时停在明确需处理状态，不无限重试。正常推进不要求用户逐轮提示“继续”。

### 补充要求的应用与证据

“已收到”表示应用保存成功；“已递交”须关联真实受理的 session/task/message 和要求快照。Accepted/Started、自然语言“知道了”均不证明模型理解、当前执行采用或要求满足。

MVP 允许在当前执行结束后的下一次输入应用补充，不要求中途强行打断工具。应用必须展示预计递交时机，在条件满足后沿现有 send/context 路径继续已授权事项；缺少 Runtime 采用证据时只显示可证明的输入关联及结果核对，不能伪称即时 steering。容量满、被拒、等待用户答复分别明确处理；停止/取消撤销自动继续意图，未知接纳先核对，不能自动重新派发。

[#142](https://github.com/HeimaoLST/Saki/issues/142) 负责唯一补充保存/递交/关联路径，[#154](https://github.com/HeimaoLST/Saki/issues/154) 消费该路径组织对话与继续；不各造一份队列/补充模型。[#31](https://github.com/HeimaoLST/Saki/issues/31) 的既有结论只证明显式下一次 send 的契约；应用自动继续的调度、恢复与失败边界仍须实际实现和验收，不由该文档推定已具备。

### 配置、资料与恢复边界

首次配置应通过 GUI 完成，不能把手动编辑 `.env` 当作最终首用流程。优先由 GUI 作为宿主复用现有配置格式、凭据注入和 Runtime 目录，不复制模型客户端或核心校验。连接目录目前是启动时装载；需要重新加载时提供明确的等待/应用重启入口，保留工作和历史，不承诺运行中透明热更新。凭据不进入消息、日志、事项、候选包或提交。

模型/职责/工具变更沿有效配置契约生效，不能仅修改 profile 显示。既有 session cwd 不可变时，为后续工作明确建立新执行上下文并保留同一联系人/事项及旧执行，不丢历史来伪造切换。新公共契约/迁移缺口由实际调用证据驱动，另行交接，需求文档本身不授权破坏性迁移。

文本资料输入与结果文件展示是两条不同用户流程，分别复用输入快照与实际产出事实。基础历史搜索只在明确范围内返回可定位结果，不冒称跨所有未加载历史或无限记忆。

切换联系人、隐藏工作区、最小化窗口不停止执行；退出须明确当前工作和收尾行为，并在重开后恢复实际已落盘状态。首版不承诺退出应用/休眠后继续运行。未知结果保持可核对，不当作失败自动重跑；失败后可从界面修正条件并继续同一事项，无需修改数据库。

以下是所有任务必须保护的现有行为，不另建“重做任务系统”的功能单。受某个改动影响时验收对应 ID。

| ID | 场景与通过条件 |
| --- | --- |
| G6-1 | 读取并展示 Runtime 返回的有效模型／配置；可选模型来源复用 Runtime，目录不可用按实际契约处理，GUI 不维护第二份模型能力表 |
| G6-2 | 空闲时 A→B→A，只有更新成功才替换有效模型显示；下一任务、恢复后的显示与真实请求一致。取消设置不提交修改，过去消息和执行事实保持 |
| G6-3 | 已接纳或正在执行时不可改活动任务配置。即使显示空闲但请求与发送竞态，仍正确处理 Runtime busy／revision conflict；失败、非法配置或不支持的 continuation 保留原有效值并解释原因 |
| G6-4 | 切换成功但响应丢失时先重读有效配置再显示结果，不盲目重试；不通过重建联系人、丢历史或直接写 Rust 存储规避失败 |

解除依赖：#105 已集成 dev `fd58ec2`；实施前核对接口、目录来源与错误语义，GUI 实际消费仍需验收。证据：Go→实际 Rust→受控 provider 请求模型，覆盖切换／busy／冲突／恢复；仅下拉框截图不算。

## G7 连接、工作要求与配置生效

范围：消费 Runtime #106 的宿主连接与增强 session 配置，并按 MVP-01 补齐 GUI 首次配置、保存、重新加载和错误恢复。GUI 作为宿主维护必要配置/凭据并注入既有 Runtime；复用单一配置来源，不另建模型客户端。OAuth、账号体系、云同步不是默认范围；具体凭据落盘机制需在 #116 设计检查点说明。

| ID | 场景与通过条件 |
| --- | --- |
| G7-1 | 新会话明确选择已有连接、模型、工作要求和内置工具，并显示工作目录；默认值来自宿主／Runtime 契约。保存与首个任务使用同一有效配置，不仅更新 GUI profile |
| G7-2 | 已绑定会话只允许契约支持的空闲更新；运行中不改变当前快照，既有 cwd 固定。只在 Runtime 确认成功后显示生效，失败不造成 GUI 与实际执行的双重配置 |
| G7-3 | 连接缺失、历史身份未知、跨 API 不兼容时展示契约允许的只读历史或明确绑定／新会话路径；不猜旧 endpoint、不自动升级旧格式。迁移需对应已批准的 Runtime 决策与回滚契约 |

解除依赖：#106 已在 dev `fd58ec2` 提供目录与增强配置；#116 首次界面配置的宿主保存/重新加载路径仍需实现核查，不能因该能力存在就假称完整 onboarding 已具备。涉及实际数据升级时检查相应授权。证据：不同连接的受控端点、配置失败／恢复和旧会话样本。没有具备条件的迁移路径时保留阻塞，不能用新建空会话冒充兼容。

## G8 随任务提交文字资料

范围：composer 中添加、预览、移除命名文字资料；首轮覆盖粘贴片段与显式选择的 UTF-8 文本文件。依赖 Runtime #108。不建设附件框架、目录扫描、PDF/OCR、向量库或自动同步文件。

| ID | 场景与通过条件 |
| --- | --- |
| G8-1 | 发送前看见本次资料名称与内容；可编辑／移除，不发送已移除资料。无法读取、非文本或超过已声明限制时给出具体反馈，不静默截断 |
| G8-2 | 文件导入时形成用户可预览的文本快照；文件之后变化不悄悄改变已展示／发送内容。再次读取必须由明确用户操作触发 |
| G8-3 | 正文和资料通过统一 task 输入提交一次，保留名称与来源边界；不拼成 system 指令，也不在正文和 context 中重复注入。被拒或本地保存失败时保留待发资料和草稿 |
| G8-4 | 接纳后资料归属该任务；不默认附到后续每次发送。历史／压缩／恢复按 Runtime 契约保存可解释来源，UI 不宣称“仅本轮使用后自动删除” |
| G8-5 | 待发资料随各联系人草稿隔离并可重启恢复；恢复后仍是保存的快照。明确接纳后清空本次待发项；结果未知时保留并禁止自动重发 |

解除依赖：#108 已集成 dev `fd58ec2`，输入限制、历史投影与错误语义已具备；GUI 的草稿保存扩展保持旧 store 可读。证据：源文件变化、移除、拒绝、重启与 Go→实际 Runtime 的单次输入核对。

## G9 多联系人并发与完成提示

范围：消费 Runtime 多会话并发能力，让已有联系人能同时执行；本阶段沿用当前绑定会话，不能替代 P3 的“同一联系人交流与工作分离”。首轮完成提示是应用内状态／未读，不默认增加系统通知权限或后台常驻服务。

| ID | 场景与通过条件 |
| --- | --- |
| G9-1 | A 在受控工具中执行时 B 可提交并实际开始；切换显示不取消任务，两个任务的消息、错误、工具和结束状态各归其主 |
| G9-2 | 对 A 停止不影响 B；A 失败不把 B 标失败；上限或同会话 busy 按 Runtime 拒绝并保留对应草稿，不在 GUI 偷加队列 |
| G9-3 | 聊天未读仅来自真实 Agent 消息；普通工作完成更新工作状态，失败/未知显示独立注意提示，查看相应结果后清除提示。工具事件不增加聊天未读；切换、重复事件、历史恢复和迟到事件不串任务或重复累计 |
| G9-4 | 多任务下断连、重载与退出继续满足 G5；按既定策略等待所有必要清理，不把切换联系人等同释放会话。并发操作同一工作目录不承诺文件隔离 |

解除依赖：#61 可从实际 stdio 入口消费、具备关联事件／取消／上限／收尾契约。证据：用协调信号证明两个实际任务重叠、定向取消和失败隔离，不靠延时猜并发。

## 开发领取与交付

1. 以 #140 和当前 Nagi MVP 里程碑中的明确分派为执行入口，复用 #111 已有工程任务，不自动展开整个 backlog。blocked 项可先做与依赖无关的准备，依赖交付后确认实际契约再推进相应实施。标题栏、主题、阅读都可能改 `view.go`，由 GUI 主责串行安排，不能因 issue 不同就并写。
2. 一个 issue 对应一个可独立验收的行为范围；主 agent 用 tmux 分派自己的子 agent，固定实例身份、动态发现地址。GitHub 记录跨线依赖和正式结果，不做主子逐步对话。
3. PR 写明对应 P／G 编号及适用共同约束，更新 `docs/design/desktop.md` 的实际行为；既有 G 项继续可追溯，新能力按 P 项补充具体验收，不把本文的需求改成已经通过的证据清单。
4. `go test ./...`、适用真实进程／原生验收与 required CI 均记录真实 SHA。完成 commit／push／PR 后仍要按有效授权推进目标分支集成与收尾；未集成保持 review，不能因截图或 CI 绿提前关闭。
5. PM／用户另外执行实际任务试用：首次配置 → 提交 → 获取可用结果 → 重启继续，记录完成情况和需要救场处。功能验收、真实试用、稳定发布分别判断。

交付证据格式：`验收 ID | 结果 | GUI SHA / Runtime SHA | 环境与步骤 | 日志／截图／测试 | 限制或剩余项`。无产线改动的验收单可以提交报告；发现缺陷则修复并补相应证据，不为清单本身添加机械测试。
