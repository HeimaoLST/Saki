更新日期：2026-10-24。状态：**当前产品定义与行为需求，待分阶段实施与验收**。依据用户本轮关于开源产品、长期联系人、事项与工作分身的讨论修订；Nagi 是 GUI 暂定名。本文件是 GUI 产品定义的权威位置，设计稿和实现文档引用本文。需求不表示功能已经完成；未决定的版本范围、接口和数据迁移仍明确列为待定。

现行视觉与交互以 [Desktop workbench](../design/desktop-workbench.md) 为唯一来源：纸白/夜林、三栏、真实消息气泡、独立 Agent 工作区。#130 实施阶段性的原生闭环；事项/看板/长期轨迹的界面与实现继续细化，原型 fixture 不作为生产功能。旧配色、工具附在聊天回复下的要求不再生效。

## 产品定义

**Nagi 是一个开源的、以长期 Agent 联系人为核心的桌面工作台。用户通过持续对话交代事项，联系人理解意图、组织工作并自主推进；用户可以随时补充要求、了解进展或深入参与具体执行。**

产品以 Grok Bot 式的完整使用体验为参照。开源和好用本身构成当前产品方向，不以发明竞品没有的交互为前提，也不承诺复制竞品全部功能、服务或性能。源代码开放如何对应许可、安装、分发和部署方式，需分别落实，不能从“开源”直接推导为任意模型可用或无需配置。

第一批用户是维护者及朋友。面向需要持续委派工作、减少逐步指导负担的人；编程、资料整理和研究都可以成为使用场景，当前未冻结单一垂直领域。代码阅读、文档整理和登录接口只是讨论／验收示例，不表示用户已经选定全部首批试用任务。

主要价值是：用户能找到持续负责的联系人；交代的事情可被跟进；执行中能继续交流；成果和未解决问题可检查。安装、配置、首次委派、补充要求、获取结果与后续继续应形成可用流程。

## 三个产品的关系

| 产品 | 职责与默认使用方式 |
| --- | --- |
| Saki | 通用 Agent Runtime，提供模型／工具执行、上下文、会话、事件与调度等共同基础，让应用开发者聚焦自己的产品；跨应用协作是发展目标 |
| Nagi（GUI 暂定名） | 联系人式桌面工作台，默认侧重用户委派、联系人自主推进和必要时反馈；它是有自身产品规则的应用 |
| TUI（名称待定） | 终端中的执行与协作入口，默认侧重用户直接观察、指导和参与工作；继续复用 Saki 的运行能力 |

自主推进与人工介入可以发生在同一项工作中；这不是 GUI 与 TUI 的能力禁区划分。目标体验是从 GUI 进入某项具体执行，在 TUI 继续参与，再回到 GUI 查看同一事项的进展，无需用户复制上下文或重新派发。共享一套 Runtime 实现尚不足以证明这个跨端流程已经实现；交付时需验证同一工作归属、状态与操作的一致性。

## 核心概念与关系

| 概念 | 产品含义与边界 |
| --- | --- |
| 联系人 X | 持续存在的协作对象，有自己的职责、工作要求和关系上下文。可以承接一次具体需求，也可以长期负责一个领域；不等于一个永不更换的 session |
| 事项（Task / Issue） | 用户希望完成的一件事，包含目标、相关要求、当前进展和结果。Task 与 Issue 在产品层为同一语义，不据此建立父子层级；一件事项可以跨多次交流与执行 |
| 对话会话 | 用户与 X 持续交流的上下文，用于理解意图、补充信息、协调事项和反馈结果；普通讨论不必自动变成事项 |
| 执行会话 | 承载某项具体工作的独立上下文与历史，可持续多次执行。X 为其组织相关要求和资料，并在需要时传递后续信息；不是完整复制所有聊天记录 |
| 工作分身 | 对“同一联系人 X 在独立执行会话中工作”的解释方式，不要求用户再创建一个联系人，也不意味着必须新增一种底层 Agent 类型 |
| 一次执行 | 运行时的一次受理、模型／工具调用到终态的过程。既有 Runtime `task_id` 标识这种执行，不能直接当作产品事项 ID；本文不修改已有协议名 |

X 对用户承担事项的持续跟进，也可以通过自己的执行会话直接完成工作。监督与执行是同一联系人在不同上下文中的职责，不强制建立“经理联系人 → 执行联系人 → 子任务”的固定层级。

一项具体的登录接口需求可以由 X 在一个执行会话中完成，不必继续拆成用户需要管理的子事项。只有独立交付、并行工作或明确专业分工有价值时才拆分或协作；拆事项、开会话和委派另一 Agent 是不同操作，不能互相自动推导。

用户把事项交给 X 时，X 是可追问进展和结果的负责联系人。协作不应让用户失去负责人，也不应在不同视图中生成同一事项的互不关联副本。跨联系人转交、共同负责与全局／项目归属的具体规则尚待设计；本文不把事项的存储位置强行定在某个联系人之下。

## 主要使用流程与行为需求

本节将已确认方向整理为可验收的目标行为，不表示下列能力都属于已交付版本。P 编号描述产品目标；后文 G 编号保留现有阶段工程验收。

| ID | 流程与要求 | 验收场景 |
| --- | --- | --- |
| P1 | 创建或选择联系人即可交流；职责与工作要求可逐步明确 | 宿主基础配置有效时，新联系人可直接接受首条请求；用户不必先填写完整角色设定 |
| P2 | 联系人承接具体事项，能组织要求并直接执行；领域职责可以对应多件事项 | 将“实现登录接口”交给 X，能找到该事项的要求与进展；不为了满足内部层级而强制再创建执行联系人或子事项 |
| P3 | 执行工作与对话分别保持可用；X 为每项工作组织独立上下文 | X 推进事项 A 时，用户仍能讨论或交代 B；B 的要求不自动混入 A，也不因对话切换丢掉 A 的进展。并发数量由明确运行边界约束 |
| P4 | 对话中的补充能够关联并影响正确事项，用户能判断是否已经应用 | A 执行中，用户要求登录方式改为短信验证码；X 保留这次变更并递交给相关执行会话，区分已收到与执行已采用。尚未采用、需要重启工作或存在歧义时明确反馈；不把整段聊天广播给所有事项 |
| P5 | 工作与消息独立：一次工作可以发零条、一条或多条消息 | 仅调用工具或无消息完成时，工作区仍可查看状态与结果；工作中发出消息不会结束执行。未读来自真实消息，失败或待处理问题在没有消息时仍可发现 |
| P6 | 联系人持续跟进多件事项；执行结束与事项完成分开判断 | A 生成草稿但仍缺用户要求的内容时，事项保留未满足部分；B 等待资料时不会消失。查看事项可找到要求、补充、结果和完成依据，取消与完成有区别；不默认每项都新增人工审批 |
| P7 | 用户可以检查和干预具体工作，随后继续由 X 跟进 | 查看某项执行、补充要求或停止时，对象明确，不误操作其他事项。停止执行不自动删除事项、历史或已经产生的结果；暂停／继续的具体机制另定 |
| P8 | GUI 与 TUI 可围绕同一工作协作，避免重复派发 | 从 GUI 的事项进入对应执行，在 TUI 继续指导后，GUI 能反映同一工作的变化；交还后 X 能继续跟进。该流程的入口、控制协调和首发范围待定，不能只用两端都能启动证明通过 |

代表性完整场景：用户让 X 实现登录接口；X 在独立执行会话中推进；用户继续和 X 讨论，并补充验证码要求；X 更新相应事项并将变更交给执行；需要时用户深入查看或指导；最终在该事项下找到满足要求的结果和仍未解决的问题。该场景用于检验流程，不将 Nagi 的用途限定为编程。

## 首个可用 MVP 的交付边界

**已确认方向**：用户于 2026-10-24 要求集中力量先交付可初步使用的 Nagi，再围绕真实使用完善 Runtime。近期交付以维护者能完成日常委派为目标；TUI 保留已有能力与回归维护，独立扩展暂缓。Runtime 的新增工作应能对应 Nagi 的具体行为缺口、实际缺陷或必要运行契约；不以通用能力清单齐全作为 Nagi 开工前提。

**PM 执行基线，待实现与实际试用验证**：首版沿用 Go/MyGo、当前三栏和气泡设计，形成下列连续流程。它是 P1–P7 的有限交付，不表示全部产品目标已实现，也不修改 Runtime 的公共契约。

| 使用步骤 | 首版必须能观察到的结果 | 对应需求 |
| --- | --- | --- |
| 启动与交代 | 维护者按准确说明配置并打开 macOS arm64 应用，选择联系人后可交流、明确交办事项；首次使用不强制完整角色设置 | P1、P2、G1 |
| 跟进事项 | 同一事项保留目标、要求、相关执行与结果。多次执行和重启不生成互不关联的副本；普通交流不强制转事项 | P2、P6、G5 |
| 边工作边交流 | 联系人推进 A 时仍能交流 B；会话、工具、消息和停止操作归属准确。实际并发受宿主容量约束，容量不足明确反馈；可用候选应配置足够容量并证明真实重叠 | P3、P5、P7、G9 |
| 补充要求 | 为选定事项保存补充要求，可查看尚未递交的内容，并明确递交给哪次执行。首版允许下一次执行才应用；当前执行不会采用时直说，不默认广播、取消重跑或无界排队 | P4 的阶段范围 |
| 获取结果并继续 | 能阅读、复制成果，找到未满足要求、待提供资料及完成依据；执行终态不自动等于事项完成。停止、失败或重启后仍能找到并继续跟进同一事项 | P6、P7、G3、G4、G5 |

“已收到”表示应用已保存；“已递交”须有 Runtime 接纳和目标执行关联。两者均不证明模型已理解、当前执行已采用或要求已满足。采用时机和证据由真实执行契约说明；缺少证据时保持待递交、待核对或明确限制。首版不为即时 steering 建立额外通用框架，也不把这个阶段限制写成 P4 已完整通过。

工作区先提供真实的未完成事项、事项详情、要求、结果和相关执行入口；完整看板、日程和长期轨迹可以随后完善。沿用纸白/夜林、消息与工作分离的视觉方向，保护草稿、中文输入、焦点和窗口可用性。原型中的 fixture 和日期不算持久化功能；基础阅读与复制不依赖完整表格、图表或文件浏览器。

首版暂不要求后台常驻、休眠后继续、自动定时、跨联系人交接、GUI/TUI 接续、人格成长、主题市场或通用插件平台。图形化配置扩展按实际使用阻碍推进；准确的既有文件配置路径可以支持首轮试用。以上能力保留后续方向，不进入本次可用性判定。

**完成判定**：提供来源可追溯的可运行候选，包含 GUI 与 Runtime 的实际源码版本、必要配置说明和已知限制；主责按上述流程完成真实模型/工具运行、停止与恢复检查，相关回归和 required CI 通过。维护者再用自己选定的真实任务试用，记录产出、未完成要求和需人工救场的位置。原生输入与窗口行为单独取证；headless 截图不替代。尚未发生的朋友试用、生产发布或 P8 验证不得计为完成。任务接收、检查点与试用记录保留在 #140，不复制到本文。

## 运行边界与待定事项

- **版本范围**：首个可用 MVP 按上节执行；P4 完整采用机制、P8 跨端接续等后续发布范围，以及具体代表任务、试用人数和周期，仍待落实。现有 #50 与 #130 的工程交付不能代表完整 Nagi 产品目标已经达成。
- **自主运行的条件**：在用户提供的目标和可用环境内自主推进，不要求逐步提示；关窗、退出应用、电脑休眠后的执行方式，本地服务／远程运行以及定时或事件触发，需分别定义，当前不承诺全天在线。
- **事项管理**：创建与合并的交互、具体状态枚举、跨联系人转交、项目归属、归档，以及完成依据的产生和复核机制需细化；一般交流不强制进入事项系统。
- **会话与上下文**：对话会话与执行会话分离的方向已明确；会话创建／复用／恢复、补充信息应用时机、历史检索、并发上限与失败恢复的接口和数据模型待实现设计。长期联系人不承诺无限上下文或自动学会所有经历。
- **开放与协作范围**：开源许可、分发／部署方式、支持的模型与工具组合，以及 GUI/TUI 协作与 Telegram／QQ 等入口的发布顺序需单独落实；不存在“开源即全部具备”的默认承诺。

## 应用与 Runtime 的职责

| 层 | 负责 | 不承担 |
| --- | --- | --- |
| GUI 应用层 | 联系人、事项、对话与工作会话的关联及上下文选择；草稿、工作目录选择、设置、主题、资料、结果、未读和窗口生命周期的产品策略 | 模型／工具执行循环、猜测执行成功、第二套 Runtime 权威执行历史 |
| Agent Runtime | 会话与任务、实际生效配置、模型与工具调用、取消、并发、执行历史、上下文预算 | 联系人、窗口、主题、业务工作流 |
| 宿主配置 | 提供模型连接与凭据，按 Runtime 契约注入 | 在 GUI 复制协议适配器或模型校验规则 |

产品层可以组织事项、选择上下文和委派工作；模型／工具／压缩循环仍由 Runtime 唯一实现。Runtime 的通用能力可以服务其他应用，不强制它们采用 Nagi 的联系人或事项模型。

## 已有阶段交付与产品目标的关系

后文 G1–G9 继承 #111 的工程验收，首轮使用现有 Go/MyGo 应用和 stdio 接口。联系人绑定一个会话、单执行槽、运行中暂不能继续发送，是该阶段的实现／交付限制，**不是 Nagi 的最终产品定义**。具体差距按 P 编号跟进，不以旧限制否定新的目标，也不靠文档更新声称代码已经具备。

macOS arm64 是首个实际验收环境，其他平台支持需单独证据。读取执行历史走 Runtime API；新能力需要真实契约与端到端验收，不规定尚未定稿的 API 字段。既有 [工程 MVP](mvp.md) 的完成条件单独保留，不因这次定义更新自动扩大或宣告完成。

旧定义的处理：GUI 仅作 Runtime 展示、联系人永久等同单 session、每条消息等同任务、一次执行成功等同整件事项完成，均不再作为产品规则。完整人格／成长机制是研究方向，不是使用联系人或实现自主工作流程的前置。

## 验收方法

后文每个验收 ID 都要填写 `PASS / FAIL / 未验 / N/A（理由）`，附候选 GUI SHA、Runtime SHA、环境、复现步骤和证据路径或链接。旧版本证据只能说明旧版本；包内 GUI 与 Runtime 可能来自不同提交，分别记录。

| 证据 | 适用与要求 |
| --- | --- |
| 行为回归 | 复用既有 Go 测试；只为真实缺陷、失败路径或非平凡不变量补测试。模型、文件读写或并发用本地受控 provider／临时目录／协调信号，不靠 sleep |
| 真实进程接线 | 涉及发送、配置、资料、恢复或并发时，Go 客户端连接实际构建的 Rust 进程；mock DTO 成功不等于接入通过。既有五项集成测试仍须实际 PASS，未设置 binary 导致 skip 不算 |
| 视觉与交互 | 视觉变化比较同场景浅色／深色、默认窗口、960×640、展开设置和宽窗口。原生操作单独记录；主题、中文组合输入、窗口按钮不能只用 headless 截图证明 |
| 真实用户试用 | 用户独立完成选定任务，记录产出、需要他人救场的步骤、恢复继续情况和反馈；开发者演示不替代用户试用 |

实现者负责模块测试，GUI 主 agent 负责评审和适用原生运行验收，QA 负责 CI 工程。无需另建 QA 人工审批队列。复用既有测试入口与 required CI，避免每个小改动重复整套人工验收；按本次影响选取相关 ID，未覆盖不得标 PASS。

## G5 执行反馈、停止与恢复共同约束

以下是所有任务必须保护的现有行为，不另建“重做任务系统”的功能单。受某个改动影响时验收对应 ID。

| ID | 场景与通过条件 |
| --- | --- |
| G5-1 | 已接受／开始／执行中／成功／失败／中断按 Runtime 事实显示；工具错误不直接等于整个任务失败。状态不能只靠颜色，失败原因可读 |
| G5-2 | 切换联系人和查看历史不停止任务。Stop 精确针对用户选中的任务；取消等待、成功、迟到取消不串到下一任务 |
| G5-3 | 断连、丢失发送响应等不能确认结果时显示未知，保留用户输入与可核对信息，不自动重发。按现有重启／加载／历史读取路径核对，恢复与查看不触发推理或重跑工具 |
| G5-4 | 关闭窗口／Cmd+Q 复用现有 drain 与退出策略；等待期间有反馈、不假称已退出。重启可恢复已落盘历史与草稿，不承诺关窗后后台继续执行 |

恢复后状态仍按 Runtime 事实判定，不能为了视觉完整度把未知改成成功。改变重连、重试、后台执行或队列策略需要独立需求，不能藏在本轮“体验优化”里。

## 开发领取与交付

1. 以 #140 和当前 Nagi MVP 里程碑中的明确分派为执行入口，复用 #111 已有工程任务，不自动展开整个 backlog。blocked 项可先做与依赖无关的准备，依赖交付后确认实际契约再推进相应实施。标题栏、主题、阅读都可能改 `view.go`，由 GUI 主责串行安排，不能因 issue 不同就并写。
2. 一个 issue 对应一个可独立验收的行为范围；主 agent 用 tmux 分派自己的子 agent，固定实例身份、动态发现地址。GitHub 记录跨线依赖和正式结果，不做主子逐步对话。
3. PR 写明对应 P／G 编号及适用共同约束，更新 `docs/design/desktop.md` 的实际行为；既有 G 项继续可追溯，新能力按 P 项补充具体验收，不把本文的需求改成已经通过的证据清单。
4. `go test ./...`、适用真实进程／原生验收与 required CI 均记录真实 SHA。完成 commit／push／PR 后仍要按有效授权推进目标分支集成与收尾；未集成保持 review，不能因截图或 CI 绿提前关闭。
5. PM／用户另外执行实际任务试用：首次配置 → 提交 → 获取可用结果 → 重启继续，记录完成情况和需要救场处。功能验收、真实试用、稳定发布分别判断。

交付证据格式：`验收 ID | 结果 | GUI SHA / Runtime SHA | 环境与步骤 | 日志／截图／测试 | 限制或剩余项`。无产线改动的验收单可以提交报告；发现缺陷则修复并补相应证据，不为清单本身添加机械测试。
